# Booking spec

## 1. Context

A caller asks for a service appointment for a vehicle, service type and dealership at a time; the system picks the bay and the technician.
Rules and their reasons live in [`docs/decisions.md`](../../decisions.md) (D-numbers); this file states behaviour only. API shapes for `POST /appointments`, `GET /appointments/{id}` and `GET /availability` are in [`openapi.yaml`](../../../openapi.yaml).
Each example below is one test.

**Service types**

**Customers / vehicles:** C1 owns V1, V2, V3.

**Conventions used in the examples**

- **Day** = 2026-10-21. Times are local (+07:00) on Day unless written otherwise.
- **Clock:** `now` = 2026-10-20T12:00+07:00 unless the example sets it. `now` comes from an injected clock; no test reads the wall clock or uses a relative date like "tomorrow".
- `avail(S, date)` = `GET /availability?dealership_id=DL1&service_type_id=S&date=date`. Start times are listed in local time.
- `book(V, S, t)` = `POST /appointments` with `{dealership_id: DL1, vehicle_id: V, service_type_id: S, start: Day t}`. `book@DL2(…)` uses `dealership_id: DL2`. No bay or technician in the body.
- K1, K2, … are fixed UUIDs used as `Idempotency-Key`.
- Calendar is empty unless *Given* says otherwise. `V1 OIL 09:00 B1/T1` = a confirmed appointment for V1, OIL, 09:00–09:30, on bay B1 with technician T1.
- **(pg)** = runs against real Postgres with requests started together; it tests the exclusion constraints or the `idempotency_keys` lock, which a mock cannot. **(fake)** = runs against a fake store that forces constraint violations.

## 3. Rules

1. The caller sends a time; the system assigns the first free bay and the first free qualified technician, by id, from the request's dealership only (D7).
2. Bay and technician must both be free for the whole `[start, end)`, half-open (D6). The technician's own hours are checked too (D4).
3. `start` aligned to 15 min, `start > now`, `start >= open`, `end <= close`, else 422. No upper bound (D1, D2, D9).
4. 409 reasons, first failure wins: `vehicle_busy` → `no_bay` → `no_technician` (D9).
5. The service type must belong to `dealership_id`, else 422. Vehicles are not dealership-scoped; `customer_id` is copied from the owner at booking (D10, D11).
6. Unknown body fields are ignored (D9).
7. Checks run in this order: 400 → idempotency key lookup → 404 → 422 → 409 (D9).
8. 400: missing field, wrong type or format, empty or null id, `start` without offset, `Idempotency-Key` not a UUID. 404: well-formed but unknown; names the first unknown in the order dealership, vehicle, service type (D9).
9. `Idempotency-Key` (D9): global client UUID. Same payload = same hash of the four schema fields with `start` in UTC. Same payload → stored response replayed (201 or 409); different payload → 422. 400/404/422 store nothing. Key row and appointment commit together.
10. `X-Request-ID` on every response, including a replay, is the current request's (D9, D13).
11. A bay or technician constraint violation retries with a fresh check, max 3 attempts, then 503 with `Retry-After` and nothing stored. A vehicle constraint violation → 409 `vehicle_busy`, no retry (D8).
12. `GET /availability` lists every aligned start where rule 1–3 would assign a bay and a technician; the vehicle is not considered (D9).

## 6. Behaviours without tests

- A key row older than 24 h is treated as absent and overwritten (D9).
- A concurrent request with the same key waits on the key row's lock. If the first commits, it replays or gets 422 — this also covers same key + different payload at the same moment. If the first rolls back (500, timeout, 503), the key row goes with it and the waiting request runs as new (D9).
- After a lost race, the retry re-runs the full check, so the 409 reason follows rule 4 (D8).

## 7. Out of scope

All from [decisions.md §3](../../decisions.md#3-out-of-scope-deliberate).

- Cancel / reschedule.
- Notifications.
- Authentication / authorisation.
- Idempotency key scoped per customer (needs auth).
- Retry of a successful booking after its key expired: gets 409 `vehicle_busy`, though the booking exists.
- Multi-tenant isolation beyond `dealership_id`.
- Technician leave / sickness mid-day.
- Per-weekday hours, holidays, lunch breaks.
- DST: handled by the IANA tz library; no DST tests (the seed timezone has none).
- Bay types, multiple skills, buffer time.
- Smarter technician assignment.
- Alternative slots in the 409 body.
- Managing reference data via API.
